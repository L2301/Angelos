**Research cutoff and access date: 2026-10-08. Status: documentary research, not a GPU benchmark.** This review downloaded no model weights, purchased or executed no inference, changed no runtime files, and created no commits. ## 3. What “native 1080p” actually means

### Latent generation is not RGB upscaling

Latent diffusion learns an image distribution in a pretrained autoencoder's representation; the learned decoder reconstructs pixels from generated latents. That normal decode is not equivalent to interpolating a tiny RGB bitmap. Compactness should mean fewer pretrained denoiser parameters, fewer latent tokens, fewer evaluations, or more efficient execution—not discarding learned image priors. [Latent diffusion paper, first submitted 2021-12-20](https://arxiv.org/abs/2112.10752).

For SANA, 32× spatial compression yields a **60×34×32 latent** at 1920×1088, or **2,040 spatial tokens** with patch size one. At 1024-square there are 1,024 tokens; our target roughly doubles them. This is a derived geometry calculation from the inspected DC-AE and transformer configs. A `32×32` latent at 1024-square is **not** a `32×32` RGB teacher output. [Sprint transformer config](https://huggingface.co/Efficient-Large-Model/Sana_Sprint_1.6B_1024px_diffusers/resolve/19683c58b7ea290e55cedd8950ae1d86ada7ef96/transformer/config.json), [DC-AE config](https://huggingface.co/Efficient-Large-Model/Sana_Sprint_1.6B_1024px_diffusers/resolve/19683c58b7ea290e55cedd8950ae1d86ada7ef96/vae/config.json).

**The SANA binning trap is material.** Both installed SANA pipelines default to selecting an aspect-ratio training bucket, generate at that bucket, then resize/crop to requested dimensions. Thus, checking only the final PNG size is insufficient. For direct 1920×1088 use `use_resolution_binning=False`, retain latent shape and pre-postprocessing decode shape, and reject a hidden resize. Both dimensions are divisible by 32. For the 2K checkpoint this also avoids turning an approximately 4-MP bucket render into an unnecessarily expensive intermediate. [Versioned SANA source](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/sana/pipeline_sana.py), [versioned Sprint source](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/sana/pipeline_sana_sprint.py).

Klein's configured VAE downsampling factor is eight and the pipeline additionally packs 2×2 latent patches, giving a **120×68 packed grid / 8,160 output tokens** at this target. Dimensions must be divisible by 16; our target is. Reference tokens increase cost further. The pipeline separately reduces reference images above 1024² pixels; explicit output width/height remain essential. These are source-derived counts, not benchmarks. [Pinned VAE config](https://huggingface.co/black-forest-labs/FLUX.2-klein-4B/blob/e7b7dc27f91deacad38e78976d1f2b499d76a294/vae/config.json), [v0.40.0 Klein source](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/flux2/pipeline_flux2_klein.py).

VAE/DC-AE **tiling** decodes portions of the already-generated target-resolution latent; it can reduce decoder activation peaks without a low-resolution RGB source. It still needs seam/color validation. It is not tiled diffusion, a super-resolution model, or evidence of accurate tiny text. A 2.09-MP image can be sharp and compositionally wrong; resolution is a necessary condition, not the quality score.

## 4. Architecture and quality review

Parameter counts below normally refer to the image backbone, **not the full pipeline**. Capability statements describe upstream models, not automatically Angelos's graph API. “Released” means weights/card or official checkpoint listing was verified; an announcement alone is insufficient. All sources were accessed 2026-10-08.

### SANA family: best efficiency fit, imperfect lettering

- **SANA (paper 2024-10-14):** 0.6B/1.6B linear diffusion transformers, a 32× compressed DC-AE, and a decoder-only text encoder. Linear self-attention reduces high-resolution attention scaling; the decoder and text encoder still carry significant cost. This is the most relevant architectural alternative to dense large flow transformers for the constrained Mac. [Paper](https://arxiv.org/abs/2410.10629).
- **Released 2K/4K variants:** the official zoo distinguishes actual 2K/4K fine-tunes from 1024 variants and provides DC-AE tiling recipes. Select the 2K BF16 checkpoint for this task rather than assuming any small SANA checkpoint is equally trained for HD. The named 2K repository was created 2024-12-20; its current pin records an Apache relicense on **2026-07-31**, not a new weight architecture. [Model zoo](https://nvlabs.github.io/Sana/docs/model_zoo/), [revision history](https://huggingface.co/Efficient-Large-Model/Sana_1600M_2Kpx_BF16_diffusers/commits/main).
- **SANA 1.5 (paper 2025-01-30; code/weights announced 2025-03-16):** depth growth to 4.8B, pruning, and inference-time sample selection improve quality/cost choices. The reported GenEval **0.81 → 0.96** includes extra inference-time selection with VILA-Judge; 0.96 is not an ordinary one-image 1.6B score. Its released 1.6B/4.8B 1024 models merit an aesthetic comparison, not automatic promotion over the explicitly 2K checkpoint. [Paper](https://arxiv.org/abs/2501.18427), [official release log](https://github.com/NVlabs/Sana).
- **SANA-Sprint (paper 2025-03-12; code/weights announced 2025-03-22):** 0.6B/1.6B one/few-step choices; the selected 1.6B recipe uses two steps. Author-reported one-step results include FID **7.59**, GenEval **0.74**, and 1024² latency of **0.1 seconds on H100 / 0.31 seconds on RTX 4090**. These do not predict Apple latency, native-HD fidelity, or Aurora brand retention. Its speed makes it a useful preview/fallback candidate, but the compression and few-step path need fine-detail scrutiny. [Paper](https://arxiv.org/abs/2503.09641), [official card](https://huggingface.co/Efficient-Large-Model/Sana_Sprint_1.6B_1024px_diffusers).

The strong practical reason to choose SANA is **high-resolution efficiency with real pretrained weights**, not a claim that it spells logos better than newer larger models. Generated lettering must be evaluated separately from exact composited lettering.

[Release log](https://github.com/NVlabs/Sana) | Those are video releases, not a newly proven still-image HD Sprint checkpoint. LTX refiners or video upscales do not satisfy direct native-HD still generation. |
| **FLUX 3 announcement, 2026-07-23; FLUX 3 Action, September** | Official pages describe multimodal early access and an open-weight 7B action model. [Announcement](https://bfl.ai/blog/flux-3), [Action](https://bfl.ai/models/flux-3-action) | No suitable released still-image checkpoint/license/pin was established here. An open action model is not evidence that the image service's weights are open. No API evaluation or paid call was made. |

This is a primary-source review of decision-relevant releases, not a claim of exhaustive global model discovery. A vendor's “best open model” or leaderboard screenshot is dated vendor evidence, not a reproducible October 2026 universal ranking. No Reddit synthesis, third-party repacks, or unsourced future releases are used for recommendations.

## 6. Campaign conditioning and product identity

**Recommended Aurora path: native-HD generated scene plus explicitly disclosed exact-brand composition.** This satisfies a useful campaign output without claiming that SANA learned Aurora identity or can spell every label. Keep two separate scorecards: raw model output and finished composition.

1. **Version the fictional brief.** Define an Aurora product reference, approved wordmark, palette, typography, required headline/CTA, allowed scene variants, product bounding box, and copy-safe region. Use synthetic adult profiles only when people are needed. These are benchmark fixtures, not factual claims about an existing advertiser.
2. **Resolve a bounded visual prompt.** Feed a concise description of scene, product category, lighting, material, camera and negative space into the model's own pretrained encoder. Do not replace Gemma/Qwen hidden states with arbitrary UPL vectors: conditioning dimensions and semantics are checkpoint-specific. A separate campaign-planning LLM may produce validated text; unload it before image inference.
3. **Generate at native target size.** SANA supplies background/art direction. If depicting the precise Aurora product is mandatory, preserve a licensed/local product cutout or render rather than expecting text-only prompting to reproduce an unseen package.
4. **Lock exact assets after generation.** Composite product pixels and approved SVG/text at final resolution; record transforms, fonts, color profile, occlusion mask and shadows. This is a hybrid generative composition, not all-diffusion logo fidelity. Do not overwrite the raw output used to score lettering.
5. **Use Klein only for a separately qualified reference-edit path.** References can improve subject resemblance, but must be tested for altered silhouette, cap shape, logos, duplicated products, and invented fine print. An instruction to preserve something is not a pixel lock.

Controllability distinctions:

| Mechanism | What it contributes | What it does not guarantee |
|---|---|---|
| ControlNet / edge-depth-pose conditions | Spatial constraints through a trained condition branch. [Original paper, 2023-02-10](https://arxiv.org/abs/2302.05543) | Object identity, exact lettering, or applicability to an arbitrary checkpoint. SANA HED weights in its zoo are separate assets, not automatic Sprint support. |
| IP-Adapter | Reference-image conditioning via additional attention; useful SDXL comparison. [Diffusers guide](https://huggingface.co/docs/diffusers/using-diffusers/ip_adapter) | Byte-exact product preservation or a universal adapter compatible with all architectures. Its small adapter file excludes base/image-encoder memory. |
| DreamBooth / subject LoRA | Adaptation to a specific subject from suitable examples. [DreamBooth, 2022-08-25](https://arxiv.org/abs/2208.12242) | Guaranteed unseen viewpoints, perfect logos or no overfitting. Training/data curation is separate work, not required for the first local output. |
| Native reference editing | Direct image-conditioned instructions in Klein/Qwen and newer unified models | A conventional `strength`/masked inpaint contract unless that exact pipeline implements it; scene areas can drift. |
| Mask plus original-pixel compositing | Explicit preservation outside the editable region | Seamless lighting/perspective or successful generative blending. Verify both masks and boundaries. |

**Capability gap:** the recommended SANA pipeline is not itself a product-identity editor. If the requirement means “all pixels, including exact product and lettering, must emerge from one generative model,” the evidence does not establish a reliable 24-GB-Mac solution. Disclose that gap rather than hiding composition or substituting a larger paid model.

### Proposed local Aurora acceptance set, not yet executed

Begin with a small go/no-go stage: two authored briefs × two fixed seeds at 1920×1088, batch one. Only after acceptable memory/latency should a larger evaluation be authorized. A practical later set is **12 briefs × 4 seeds = 48 outputs per model**, with equal sample budgets and no cherry-picking. Include packshot, reflective materials, hands holding product, busy outdoor scene, minimal luxury scene, two products, constrained colors, reserved copy space, long headline, small label, mixed-language text, and difficult product-angle cases. Hold out briefs used for prompt iteration.

| Axis | Measure / artifact | Proposed hard gate or reporting rule |

| Native HD | Requested dimensions, latent dimensions, pre-resize decode dimensions, final crop rectangle, transformation log | Every accepted frame decodes at 1920×1088 with no RGB enlargement; raw image retained. |

## 8. MPS, CPU, CUDA, and browser limits

### What was actually checked on this host

Read-only checks returned **`Mac14,2`, 25,769,803,776 physical bytes (24 GiB), MPS built and available, and `torch.mps.recommended_max_memory()` = 19,069,665,280 bytes (about 17.76 GiB)**. An initial sandboxed check reported MPS unavailable; a permission-approved hardware-only check outside that sandbox returned available. Neither result involved model loading or inference. The recommended working-set figure is not free memory or a promise of safe allocation.

**Unified memory is shared with macOS, browser, editor and CPU tensors.** CPU offload on Apple does not manufacture separate physical RAM; it can reduce MPS residency while leaving total pressure high. Loading two complete pipelines simultaneously is the wrong baseline. Bfloat16 weight files do not imply that every operator/activation uses BF16, and safetensors disk bytes do not equal peak process memory. [Diffusers MPS guidance](https://huggingface.co/docs/diffusers/optimization/mps).

Proposed order for an authorized local test:

1. Close unrelated heavy applications; run one worker and one image. Explicitly choose BF16 for transformer/text encoder where the current MPS kernels support it. The proposed first decode uses **`pipe.vae.to(dtype=torch.float32)` plus tiling**, not an all-FP32 pipeline. Installed Sprint code casts latents to the VAE dtype before decode. This mixed-precision proposal requires output/NaN checks and actual memory measurement; neither BF16 MPS nor tiled FP32 DC-AE execution was exercised here. A dtype rejection is a reported incompatibility, not permission to silently inflate the whole pipeline to FP32.
2. Enable DC-AE tiling before HD decode. The installed API supports `tile_sample_min_height`, `tile_sample_min_width`, `tile_sample_stride_height`, and `tile_sample_stride_width`; a conservative experiment is 512-pixel tiles / 448-pixel strides, both 32-aligned. Inspect seams and record the policy. This reduces decoder peaks, not transformer/text memory.
3. If necessary, encode a bounded prompt first, retain the exact embeddings **and attention mask**, release the text encoder, then load/run the transformer and decoder. Cache embeddings only with encoder revision, prompt and preprocessing version bound to the key. This trades load overhead for headroom and changes implementation architecture; it is a proposal, not existing support.
4. Release the campaign-planning LLM and stale pipelines before generation. Use a seeded **CPU `torch.Generator`** for MPS-compatible noise creation; same seeds across backends need not imply byte-identical images.
5. Do not disable the MPS high-watermark guard to make a demo appear successful. PyTorch documents that a zero high-watermark ratio disables the limit and can cause system failure. If `PYTORCH_ENABLE_MPS_FALLBACK=1` is chosen for unsupported ops, disclose mixed CPU/MPS execution and changed timings. [PyTorch 2.14 variables](https://docs.pytorch.org/docs/2.14/mps_environment_variables.html).
6. If kernels or memory fail, record the failure. A fully CPU FP32 pipeline is slower and may consume much of the same 24 GiB; it is not an assured HD fallback. Stage components if implementing it. No CUDA/cloud job, quantized repack or model download may be initiated automatically.

SANA's linear attention and smaller latent grid make it the best *feasibility-first* family among the verified candidates here. The 2K model's 20-step CFG path can take much longer than Sprint's two-step guided path. **No seconds-per-image or guaranteed “fits in 24 GB” claim is warranted without execution.** Sprint 1.6B is a speed alternative, not necessarily an OOM escape from SANA 2K: their main file footprints are almost equal. The now-verified **0.6B Sprint saves approximately 2.03 GB of transformer files versus Sprint 1.6B**, but retains the same large text encoder and decoder. This justifies first-run ordering, not a native-HD quality guarantee.

On a later separately authorized CUDA machine, 24-GB discrete VRAM would be a reasonable *test target* for Klein with offload/tiling, not a measured minimum. Quantization improvements reported for NVIDIA FP8/NVFP4 or Nunchaku are hardware/software-specific; they cannot be assumed to work through stock Diffusers MPS. Training and distillation memory are a different budget from inference.

### Browser delivery is not browser diffusion

Use the browser to edit briefs, show native-resolution output, compare crops, and inspect provenance, while a local Python worker performs generation. An HD RGB image is only about 6.27 MB uncompressed; a multi-GB model plus activations is a very different workload.

An ONNX/WebGPU port needs supported operators, precision and shader paths, explicit tensor/buffer partitioning, downloadable/cached component artifacts, and measured device limits. ONNX Runtime's official web guide notes the 2-GB protobuf limit (external data required) and its documented 4-GB WASM-address-space limitation for large models. This is a limitation of that documented runtime route, **not a universal 4-GB cap on all browser GPU memory**. A 5.23-GB Gemma encoder alone makes a naive single-session port unsuitable. [ONNX Runtime large-model guide](https://onnxruntime.ai/docs/tutorials/web/large-models.html).

Neither a desktop MPS run nor a mobile research demonstration proves Safari/Chrome WebGPU support. No verified ready-to-run native-HD browser package for the selected pins was established. Do not claim WebGPU inference from an image displayed in a canvas, and do not shrink the model to an untrained 22,000-parameter network to make that claim.

### Separately reported native-HD execution

On 2026-10-08, the user reported that the implementation successfully generated **one SANA-Sprint 0.6B image on MPS at 1920×1088**, then cropped **four rows from the top and four from the bottom** to 1920×1080. The reported run passed and took **135 seconds including model loading**; the visual assessment was favorable and photographic. These are reported execution observations, not measurements or image inspection performed by this research review.

See the forthcoming [HD execution report](HD-EXECUTION.md) for the execution record and supporting artifacts. One successful image supports a bounded pretrained native-HD demonstration; it **does not qualify a campaign student, demonstrate personalization, establish product/brand fidelity, or validate the proposed Aurora acceptance set**. The timing is not steady-state inference latency or a service-level guarantee. **No paid jobs remain permitted.**
